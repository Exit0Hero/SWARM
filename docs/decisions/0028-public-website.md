# ADR-0028: Public website: static, read-only showcase on Vercel

- **Status:** Accepted
- **Date:** 2026-11-22
- **Phase:** release engineering (post-0.1.0)

## Context
The project needs a public website on Vercel. SWARM's simulator is a Python package. Its dashboard
(ADR-0026) is an unauthenticated standard-library server, built for localhost only, that runs
episodes and writes files. The brief rules out mock data, fake live functionality and exposing the
local dashboard. It also says to fall back to a read-only demonstration if public execution cannot
be secured.

## Options
1. **Run simulations in Vercel Python functions.**
   - It is technically possible, since one episode takes about 0.1–1 s.
   - But public execution needs per-client rate limiting and a store for quotas. That means extra
     infrastructure (a KV store and secrets) that this repository cannot provision or test before
     deploying.
   - It would also run the simulator on every page visit, even though the outputs are
     deterministic and identical for a given seed.
2. **A separately hosted Python backend.** This needs a second hosting account, persistent
   compute and authentication or rate limiting. It also adds an always-on attack surface for a
   research showcase.
3. **A static site of prerecorded real runs.** **Chosen.**

## Decision
- **What is served:** Vercel serves `web/` as static files. `buildCommand` and `installCommand`
  are empty, there is no `api/` directory and no serverless function, and `.vercelignore`
  uploads only `web/` and `vercel.json`.
- **Where the data comes from:** `web/data/` is generated by `scripts/build_site_data.py`:
  - four episodes recorded with the normal runner through the dashboard recorder, with their
    MuJoCo 3D analysis;
  - results copied from the archived pre-registered analyses (Phases 3 and 7) and the exploratory
    benchmark, each with its source path.
- **Integrity, checked in CI** (`tests/test_site_data.py`):
  - the current simulator must reproduce every recorded episode's event-stream hash;
  - every published number must match its archive.

  If behaviour changes, CI fails until the data are regenerated.
- **Labelling:** the page labels every run "Prerecorded" and says that nothing on the site runs a
  simulation. New simulations run through `swarm dashboard` on the user's own machine.
- **Security headers** (`vercel.json`):
  - CSP: `script-src 'self'`; no `eval`; styles allow inline and Google Fonts; fonts only from
    `fonts.gstatic.com`; `connect-src 'self'`; `frame-ancestors 'none'`;
  - `nosniff`, `X-Frame-Options: DENY`, a referrer policy and a permissions policy.
- **Viewer code:** `web/assets/app.js` reuses the dashboard's frame format and drawing approach,
  but it is a separate read-only viewer. The local dashboard is not deployed.

## Consequences
- **Nothing to exploit:** there is no server-side execution, so no simulation endpoint, no
  arbitrary configs, no checkpoint loading and no file export. Nothing is persisted.
- **Updating the site:** regenerate the data (`python scripts/build_site_data.py`, which needs
  the `sim3d` extra for the 3D figures), commit, and merge. Vercel redeploys `main` through its Git
  integration.
- **Revisiting live execution** (option 1 or 2) needs its own ADR, with rate limiting,
  authentication and resource limits that are tested before launch.
